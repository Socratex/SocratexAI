# flow-panel

Colloquial name: **"kropki"** (the dots), after the moving dots on its lines.

A side panel for Claude Code (desktop app). It costs no model tokens: it only listens to engine events and draws SVG.

- Layout: a vertical file-tree, left-aligned (10px margin) with rounded elbows. `User` on top, `Claude` below, one branch per path.
- Trunk `User -> Claude`: growth of the account's 5-hour limit in percent since the mod first saw the current window.
- Lines from Claude: what each path cost: US cents (¢, rounded like the percent figures) below one dollar, then dollars with one decimal ($1.2), from the engine's own cost ledger (`$.session.usage().cost`, the figure `/cost` shows; free to read). Sub-agents get the ledger growth over their own turns; tools, MCP and skills get their result size priced at the session's average dollars per weighted token (`...` until known); a Session tile shows the sum of its branches while it works (so the figure grows as they finish) and, once idle, what it really spent since its last prompt. Parallel agents blur each other a little. The figure between User and Claude is the sum of the branches below.
- Dots: an active line has two lanes. The request goes down on one side of the line (west/south), the result comes back up on the other (east/north); the two lanes are 12 px apart and start half a second apart. Every second each lane sends a batch of 1 to 8 dots, in a row 1 px apart, all at the same speed (120 px/s). Up lane: batch size is the tier of the result's token pace (tokens per second of the turn or tool result: input + output + cache-write over wall time). Down lane: the tier of the request's pace (size of the call arguments over the call's duration); only tool calls have it, other lines send one dot down. Eight tiers, from almost nothing to tons; thresholds (220/375/560/800/1250/2300/5500 tok/s) are the p10..p95 of the owner's own turns and live in one table, `TIERS`, in `hooks/register.tsx`. The line pulses with each batch. Timing follows the wall clock, so a redraw does not restart the dots.
- `/btw` (and `/subtask`, `/fork`): a fork that a command starts, not the Agent tool, shows as a pink `Side` branch with its own cost and dots, active while its turn runs. The engine gives no field that tells these three commands apart, so they share one branch.
- Toggle: a button above the drawing picks the figure on every line: cost (¢), time or tokens (shown in K, then M, one decimal; fresh tokens the path moved: agent turns = input + output + cache write, tools = request + result) and time (seconds and minutes, summed execution time, counting live while a path runs: the picture pre-draws one label per second for 70 s and a SMIL animation swaps them, and while anything runs one redraw per minute refills them; at most 6 ticking times per drawing; a session shows the sum of its branches, so parallel work adds up). The choice is this pane's own and is not shared with other sessions.
- Colours: user blue, Claude orange, sessions and sub-agents cyan, tool burgundy, background command or monitor (/tasks) dark blue, MCP purple, skill yellow, desktop-app tools orange, side forks pink. A component working right now has a border in a lighter shade of its own colour; an idle one has none. Red ring = error, grey = background work. Each session started from here gets a small shift of the whole palette (hue a few degrees, lightness a little up or down; table `SHADES` in `hooks/register.tsx`), shared by its tile and everything below it: fills, active borders, glow, lines and dots. This session's own tree is unshifted; state rings and text keep their colours because they carry meaning.

## Always on

`tools/install.py` adds `CLAUDE_CODE_PLUGIN_DIRS` (this folder) to the `env` block of `~/.claude/settings.json`, so the mod loads in every session after a restart. The panel opens at session start and again at every prompt.

## Switching off (outside SocratexAI)

Set `FLOW_PANEL` to `0` in the `env` block of a settings file; the project value wins over the global one.

- Everywhere: `~/.claude/settings.json` -> `"env": { "FLOW_PANEL": "0" }`
- One project: `<project>/.claude/settings.json` (or `settings.local.json`) -> `"env": { "FLOW_PANEL": "0" }`
- Back on for one project while globally off: `"FLOW_PANEL": "1"` in that project.

`/flow-panel` opens the panel by hand even when it is switched off. Changing the env needs a new session.

## Limits

- The limit figure is the whole account's, so other sessions inflate it and the learned factor.
- Lit paths (moving dots) follow the main turn. A state change that would draw the same picture is held back, not written, so the pane redraws (and blinks) only when something visible changes. SVG is pinned top-left, margin 5px.
- Sessions started from here (start_session) show as grey "Session N" tiles holding their own full tree, nested. Each session with the mod writes its tree to `$SOCRATEX_HOME/local/flow/<session id>.json`; in the desktop app the parent reads the app's own session store (`claude-code-sessions`: who started whom, titles, archived) and draws exactly its own non-archived children; elsewhere it attaches a file only if the file was born within 2 min of its start_session call and the session's first prompt starts with that call's brief, so sibling sessions are never attached.
- The last view is saved to `local/flow/` (one file per session) and restored at session start, so a restart does not begin empty.
- A session that ends or is archived marks its file as ended, and an idle file not updated for 3 minutes is dropped, so finished sessions leave the tree (an idle live session disappears after 3 minutes of silence).
- A new prompt clears the segments; only paths used since then are shown.
- Background agents (`run_in_background`) survive a new prompt: they stay as a running (grey) branch with moving dots. The agent start event says outright that it is a background one. The end comes from the engine's agent list (`$.agent.list()`), read by the 3 s poll: status completed, failed or killed, or the row dropped (a freshly started agent gets 10 s of grace before "not listed" counts as over). No time guess is left.
- Background tasks (what `/tasks` lists besides agents): a background Bash (`run_in_background`, Ctrl+B, or moved there by a timeout) and a Monitor show as one block each, with a grey ring, from the moment the tool returns its task id until the task ends. The mod has no `/tasks` list it can poll (no API: the types expose none, `$.agent.list()` holds only agents), so it follows the events and, as a cross-check, the `background_tasks` list that the engine puts on every Stop event (in-flight shells, monitors, subagents; an unlisted task, or one listed as completed / failed / killed, is closed after a 10 s grace from its start). That check runs at each turn end, not every 10 s, and does not fire while the session sits idle: the tool result gives the id, the end is the engine's task notification (a prompt with origin `task-notification`, status completed / failed / killed), a `TaskStop` result, or a finite Monitor's deadline (+5 s backstop). Such a notification is not the owner's prompt: it neither clears the panel nor restarts the prompt's cost. A command that never reports an end runs without a time limit, as long as this process saw it start; a task still running in the stored view that was not seen starting (the session was restarted, the task ended unheard) is closed by the next poll. Label: the task name cut to 8 characters (Bash: description, else the command; Monitor: description); the tooltip holds the full name. A failed task gets the red ring for a few seconds. The first end notification (and the first notification that is not an end) is written once to the debug log (`$SOCRATEX_HOME/local/flow-debug-<session>.log`, lines `task end ...`), to compare with `/tasks`.
- Re-check of background tasks (best effort, unverified live): while the only live things are background tasks (main turn idle, no agent, tool or side fork running), the mod calls the engine's `GetTask` tool once a minute per task (`$.tool.call`, raised by the mod itself) and closes a task that the answer shows over: status completed, failed, killed, stopped or cancelled, or an explicit "unknown task" answer. The timer exists only while that condition holds; it is dropped when other work starts or no task remains, and it redraws nothing by itself (only a closed task does). Rules of doubt: a thrown error, a denied call, an unknown shape or status leaves the task running (a longer glow, never a false close); "unknown task" closes only after `GetTask` has answered about some task once (so its ids are known to be valid; otherwise an id the tool cannot read would close everything); a task gets the same 10 s start grace. After 3 useless answers in a row the re-check gives up for the rest of the session and logs it once. It is not proven that `GetTask` accepts the ids of a background Bash or a Monitor; the debug log (`$SOCRATEX_HOME/local/flow-debug-<session>.log`) gets one `recheck first call ... raw ...` line with the raw first answer and one `recheck outcome <kind>` line per distinct outcome (ended, missing, running, unknown, error), to check it live. **Cost: check `/cost` once.** It is a mod tool call, not a model turn, but whether it spends model tokens or lands in the transcript is unknown. Switch off with `FLOW_TASK_RECHECK` set to `0` in the `env` block of a settings file (new session needed); the Stop-event check keeps working.
- No usage, no dots: a task has no token or cost data, so its block is drawn like the others but without dots: the line pulses, the block pulses and glows, and a small grey blinking status LED sits in its top-right corner. The figure on its line is only time (ticking); cost and tokens show "-" and the task is left out of every sum, time included (a dev server running for 30 minutes does not inflate a session's or the total time). Background agents have per-turn usage, so they keep their dots and get no LED.
- Merged blocks: per category (tool, MCP, skill, app) the leaf blocks (no children) that cost under 1 cent merge into one block ("Tools", "MCP", "Skills", "Apps"), but only when a category has two or more of them; a single cheap block stays as it is. The threshold is always by cost, whatever the toggle shows, so blocks do not jump when the unit changes. The merged block shows the sum in the chosen unit; its tooltip lists the members in that unit, one per line ("Grep 0.2¢", "Read (x2) 0.4¢"; the same name twice is one line with a call counter). It is active if any member is, the red error ring beats the grey one, and it has the LED if any member has one. Blocks with an unknown cost ("...") and tasks are never merged. The merge happens before sessions are folded; the session rules are unchanged.
- Figures refresh after each main turn, not continuously. Redraws are batched to one per 2 seconds, with dots keeping their phase, to avoid blinking.
- Size guard: the pane refuses an SVG over 131072 characters and then shows "nothing to show yet" for the whole panel. Idle sessions sink to the bottom of their level and show no children. From 10 idle sessions on one level they become one tile "12 sessions" with their summed figure and a tooltip of their names, one per line (nested ones indented); working sessions keep their branches. A drawing still over 126000 characters folds all idle sessions, then loses moving dots and ticking times, then fewer nested session levels.
- At most 12 blocks per session level (`MAX_NODES`); the idlest finished one is dropped first, a running one never.
- Tuning constants (font, weights) are at the top of `hooks/register.tsx`. The pure parts have tests (`tools/tests/test_flow_*.py`): `<tiers>`, `<merge>`, `<tasks>` and `<recheck>` blocks, and the whole drawing with fixed data.
